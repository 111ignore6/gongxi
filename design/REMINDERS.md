# 提醒与回应：设计草案（v0.1）

状态：待评审。本文只定义产品语义与验收，不含实现。v0.1 吸收 Codex 对“已回应判定、状态机、期限、撤销、汇总与事件隐私”的意见。

## 1. 为什么需要三种状态

组织者要的是“谁读过、谁该回、谁还没处理”能被看见，而不是再做一个消息红点。三种状态**互不替代**：

| 状态 | 含义 | 谁产生 | 能否互相推导 |
|---|---|---|---|
| 未读 | 某人还没读到这条消息 | 系统按阅读水位计算 | 否 |
| 需回复 | 作者明确请某几位回应 | 作者显式标记 | 否；读过≠已回，回了≠处理完 |
| 待处理 | 被指派的具体事项 | 作者用 `action_for` 指派 | 否；处理完≠读过 |

## 2. 规则

1. **默认不催办**：普通发言不产生“需回复”，不产生逾期。
2. **需回复必须显式**：作者选定对象（可多人），期限可选；无期限永不逾期。
3. **“已回应”只认带引用的回复**：目标成员对原消息发 `reply_to=原消息` 的直接回复才算回应；v1 **不允许**只点按钮就记为已回应。按钮只负责带着引用上下文打开回复框。
4. **回应只关闭该成员的请求**：不改变 `action_for` 的待处理状态，也不代表事项完成。
5. **回复不自动完成**：待处理只能由被指派人标记 `handled/no_action`。
6. **阅读不升级**：读到消息不会自动把“需回复/待处理”变成已处理。
7. **一次请求一次结果**：v1 不支持重新打开；`pending → responded` 或 `pending → withdrawn`，之后只读历史。
8. **提醒只在应用内**：客户端轮询/在线时更新，不承诺离线唤醒、不推送系统通知。
9. **最小可见**：需回复对象只对发起人、目标对象、组织者可见；普通成员在 `state` 与 `events` 都拿不到他人请求的目标列表、回复时间或撤销原因；被过滤的事件不阻塞 cursor。

## 3. 数据模型（建议）

`reply_requests` 每次“作者请某些人回应”生成一行：

| 字段 | 说明 |
|---|---|
| `id` | 请求 ID |
| `message_id` | 原消息 |
| `member_id` | 目标成员（一人一行，多人请求生成多行） |
| `requested_by` | 发起人 |
| `due_at` | UTC；可为空；不接受过去时间；仅发起人可改/清 |
| `status` | `pending / responded / withdrawn` |
| `response_message_id` | 只有 `responded` 时有值，必须是 `reply_to` 原消息的发言 |
| `responded_at` | 回应时间 |
| `withdrawn_at` | 撤销时间（仅 `status=withdrawn` 时有值） |
| `withdrawal_reason` | `withdrawn / reassigned`；仅 withdrawn 时有值，可见性受 §7.5 限制 |
| `reassigned_from` | 重指派时指向旧 request id；新行才有 |
| `created_at` | 创建时间 |

- 阅读水位沿用 `read_states`，不新增字段。
- 成员被撤销时，其 `pending` 请求置为“目标已撤销”展示态（不写 responded、不写 withdrawn），由发起人或组织者决定重指派或撤销；历史保留。

## 4. 界面

1. **议题条/侧栏**：三个独立计数（未读 / 待我回应 / 待我处理），不合并成一个数字。
2. **抽屉“我的待办”**：分「待我回应」「待我处理」「我发起的需回应」三组。
3. **消息下**：需回复显示“待 X 回应”小签；目标对象看到“回应”按钮（带引用打开回复框）；发起人看到撤销。
4. **处理指派汇总**：按人显示 `pending / handled / no_action` 与待处理人数，不做消息级二元状态；标题叫“我发起的处理指派”，避免与 `no_action` 混淆。
5. **逾期**：只有设了期限且过期时才显示红色小字；过期后仍为 pending，不自动取消；回应后从待回应/逾期计数移出，但保留“逾期后回应”的历史标记。
6. **空态**：没有待办时显示“当前没有需要你回应或处理的事项”，不做成庆祝动画。

## 5. 验收判据

- 未读：A 读过后 A 的水位前进；B 的未读数不变；组织者能看到 A 已读，普通成员看不到 B 的。
- 需回复：作者标记后目标成员看到入口；目标只看不点、没有带引用回复时状态保持 pending；发出 `reply_to` 回复后自动 responded 并记录 `response_message_id`；只点按钮不改变状态。
- 回应边界：responded 只关闭该成员的请求，另一目标仍 pending；`action_for` 的待处理不变。
- 状态机：一次请求只能从 pending 走到 responded 或 withdrawn 一次；重复操作返回 409/幂等不变更。
- 期限：`due_at` 存 UTC；未设期限永不逾期；到期只显示逾期、仍 pending；发起人可清期限；过去时间被拒。
- 撤销成员：pending 目标被撤销后显示“目标已撤销”，不自动完成、不计普通逾期，可重指派或撤销。
- 汇总：多人指派按人显示状态与待处理人数，不出现消息级二元状态。
- 事件隐私：`reply_request.created/responded/withdrawn` 只对组织者、发起人、目标返回；普通成员 state/events 无目标列表、回复时间、撤销原因；被过滤事件不阻塞 cursor。
- 隔离：普通成员在 `/api/state` 与 `/api/events` 都拿不到他人的需回复记录。

## 6. 非目标

- 不做系统级推送/邮件/桌面通知。
- 不做“已读即已回”的自动推断。
- 不把普通消息默认变成催办。
- v1 不支持重新打开已结束的请求。

## 7. 实现契约（v0.2 追加，依据 Codex 2026-10-29 提议）

### 7.1 原子化回应

- 仅当「发言者 == 该 request 的目标」且「`reply_to` 精确等于原消息」且「同议题」时，服务端在同一事务内把该目标 `pending` 请求改为 `responded` 并写 `response_message_id`。
- 其他人引用原消息不关闭目标请求；原作者自引用不误触发。
- 失败时整体回滚（发言与状态同生共死）。

### 7.2 幂等与冲突分开

- **创建请求的幂等键**：`POST /api/reply-requests` 必须带 `Idempotency-Key` 请求头；唯一范围为 `(message_id, requested_by, key)`，重试返回同一批目标行，不重复生成、不重复发事件；
- 回复类请求沿用发言的幂等键；
- 同一 key 重试：返回原结果，不重复建请求、不重复发事件。
- 对已是当前终态的请求重复提交：幂等返回当前状态（200）。
- `pending` 以外的非法状态转换（如 responded → withdrawn）：返回 **409**。

### 7.3 目标约束（服务端校验）

- **只能由原消息作者创建**：服务端校验 `requested_by == message.author_id`；v1 不开放组织者代建（如需，后续加显式 `owner_proxy` 标记并审计）；
- 只能请求其他活动成员：不能请求自己、不能请求已撤销成员；
- 多人上限（建议 20 人）；
- `due_at` 用 UTC，服务器校验必须为未来时间；
- 只有 `pending` 请求允许改/清期限，且只能由发起人操作。

### 7.4 撤销与重指派审计

- 重指派**不覆盖**旧 request 的 `member_id`：旧行置 `withdrawn`（原因 `reassigned`），新建指向新成员的 request，用 `reassigned_from` 关联前后。
- 撤销原因只对组织者与发起人显示；目标名单仍受最小可见约束。

### 7.5 字段可见性矩阵

| 字段 | 组织者 | 发起人 | 目标本人 | 无关成员 |
|---|---|---|---|---|
| 请求对象存在 | 可见 | 可见 | 可见（自己） | **不可见** |
| `status` | 可见 | 可见 | 可见（自己） | 不可见 |
| `due_at` | 可见 | 可见 | 可见（自己） | 不可见 |
| `response_message_id` | 可见 | 可见（是否回应） | 可见（自己） | 不可见 |
| `responded_at` 精确时间 | 可见 | 仅状态，不给精确时间 | 可见（自己） | 不可见 |
| 撤销原因 | 可见 | 可见 | 不可见 | 不可见 |

### 7.6 接口草案

- `POST /api/reply-requests` `{message_id, member_ids[], due_at?}` → 200（首次与幂等重试同码），逐人生成行；校验 7.3。
- `PATCH /api/reply-requests/{id}` `{status:"withdrawn"}` 或 `{due_at}`：仅发起人、仅 pending；组织者不代理（如需代理另立规格）。
- `POST /api/messages` 带 `reply_to`：按 7.1 事务化回应。
- `GET /api/state`：只返回 7.5 允许的行；`/api/events` 同步过滤，未授权事件不阻塞 cursor。
